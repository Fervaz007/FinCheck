## Context

FinCheck (Expo + React Native + SQLite/Drizzle, local-only, single user) currently spreads "how much do I owe and does it fit my budget" across five screens (Deudas, Recurrentes, Compromisos, Categorías, Presupuesto) that don't share a data model:

- `categories.budgetGroup` was meant to feed budget compliance but never did — `computeBudgetCompliance` (`presupuesto.tsx`) uses hardcoded group names (`necesidades`/`deudas`/`ahorro`/`ocio`), not real category tags.
- `commitments` duplicates what a recurring/periodic debt already implies (an amount due every N periods), just as a separate manually-managed entity the user has to remember to update.
- Every `income`/`expenses`/`debtPayments` row carries an `accountId` used to compute a per-account ledger (`accountsDao.getAccountBalanceCents`), but the user has confirmed they never look at per-account balances — only the pooled "disponible" total (`availableCents = income - expenses - debtPayments`), which already exists as a separate, account-agnostic calculation.
- `settings.debtLimitPct` is a free-floating percentage disconnected from the budget rule the user actually activated.

This is a single-user, local-SQLite app with no server/migration audience beyond the one device — schema changes here are simple column adds/drops, not staged rollouts.

## Goals / Non-Goals

**Goals:**
- One place (Deudas) owns every periodic financial obligation — parent/child debts, their budget-rule type, their recurrence, and their biweekly reserve.
- The budget rule the user activates is the single source of truth for both "what type is this obligation" and "what's my debt limit."
- Money tracking matches how the user actually thinks: one pooled "disponible" number; there is no accounts concept at all — the user tracks money by logging income/expenses, never by declaring a balance somewhere.
- Reuse the existing recurrence/reconciliation catch-up engine (`computeOccurrences` + `runReconciliation`) for the new biweekly reserve accrual instead of inventing a parallel scheduling system.

**Non-Goals:**
- Per-account real balance tracking (explicitly dropped by user decision).
- Interest/amortization math for debts (unchanged — still simple monthly-payment × remaining-months estimates).
- Multi-user/multi-device sync (out of scope, unrelated to this change).
- Redesigning the visual theme/components — only screen composition and data flow change.

## Decisions

### 1. Monitoring is per-allocation-row and unlimited, not a single "debt-limit" row — and never blocks debt creation
Revised twice after real usage: first from "match by label text" to "one explicitly-marked row," then — after the user found a single mandatory debt-limit row confusing and unnecessarily blocking — generalized further to **any number of monitored rows**, decoupled entirely from whether a debt can be created.

Each `budgetRuleAllocations` row gets an `isMonitored` boolean (renamed from the earlier `isDebtLimit`) — any number can be `true` on a rule, including zero. A monitored row means: track its actual-vs-allocated compliance on Inicio (`dashboard`), and factor it into overall health status (`financial-health`). An unmonitored row is still a perfectly valid Tipo to tag a debt with — monitoring is purely about which groups the user wants the app watching, not about which groups exist.

- **Alternative considered (first pass)**: match by label text (`label.toLowerCase() === 'deudas'`). Rejected — rule labels are free text the user types (could be "Deudas", "Tarjetas", anything); text matching is fragile and silently breaks if the user renames the row.
- **Alternative considered (second pass, actually implemented and then reverted)**: exactly one row per rule marked `isDebtLimit`, with debt *creation* itself blocked until that row exists. Rejected on user feedback — conflating "which row is my debt-tracking reference" with "whether I'm allowed to register a debt at all" was confusing and overly strict; a debt only actually needs an active rule to source its Tipo options, nothing about monitoring.
- **Decision**: debt creation requires only an active budget rule (see `debts`), never a monitored row. Monitoring is purely a display/health concern, fully decoupled.
- **Fallback when no row is monitored**: `computeFinancialHealth` returns `sin_limite` and the Inicio compliance card shows nothing, rather than crashing or defaulting to a fake percentage.

### 2. Reserve accrual ("Apartados") is a field-based mechanic on `debts`, not a new `recurringTransactions` kind
Add to `debts`: `periodicity` (`'mensual' | 'bimestral'`, nullable — only meaningful when `isRecurring`), `isRecurring` (boolean), `reserveAccumulatedCents` (integer, default 0, seeded from the "Apartado inicial" field at creation), `reserveLastAccrualDate` (nullable text date).

A new pure function `computeReserveAccrualCents(periodicity, currentTotalCents)` returns the per-cutoff share (`/2` for mensual, `/4` for bimestral). A new step in the reconciliation pass (reusing `computeOccurrences` with `SEMIMONTHLY_FIXED` — the existing día-15/último-día pattern — anchored at each recurring debt's `startDate`) walks every `SEMIMONTHLY_FIXED` cutoff between `reserveLastAccrualDate` (exclusive) and today (inclusive), and for each one adds the per-cutoff share to `reserveAccumulatedCents`, using the **current** derived total for parent debts (`deriveParentMonthlyPaymentCents`), exactly like the existing debt-payment reconciliation already re-derives the amount on every run (`reconciliation.ts` lines ~58-64) — so a parent's reserve always tracks its live children sum, never a stale snapshot.
- **Alternative considered**: add `'debt_reserve'` to `recurringTransactions.kind` and let the existing `runReconciliation` loop handle it like income/expense/debt_payment. Rejected — reserve accrual doesn't generate a row anyone confirms/sees individually (unlike a scheduled `debtPayments` entry); it's a running counter on the debt itself, and forcing it through the occurrence-log table (`recurrenceOccurrences`, which has a unique `(recurringTransactionId, occurrenceDate)` index designed for generated entities) adds ceremony with no benefit. A dedicated `reserveLastAccrualDate` column is simpler and keeps reserve accrual visibly independent from "is this bill due yet."
- Reserve accrual and the existing scheduled `debtPayments` generation (also driven by `isRecurring` + `periodicity`→day-based recurrence config) run side by side, keyed off the same debt, but are independent: a debt can have a `debtPayments` row still "scheduled" while its reserve keeps accruing normally.

### 3. Reserve reset is tied only to payment confirmation
`confirmPayment(paymentId)` (no `accountId` param anymore) sets `reserveAccumulatedCents = 0` and `reserveLastAccrualDate = null` on that payment's `debtId` in the same transaction. No standalone "reset" action exists — matches the user's explicit requirement.

### 4. Accounts are removed entirely; income gets a free-text `origin` field instead
This decision was revised after the "manual reference list" version (a declared, editable balance per named account) was actually implemented and tested: the user confirmed they never touch a declared balance — they track money by logging income, not by typing a number into an account. Once that's true, a manually-declared balance has no reader anywhere and a fixed account catalog serves no purpose beyond letting the user pick a word from a list they'd rather just type. So instead:
- The `accounts` table, `accountsDao.ts`, `useAccounts.ts`, and `cuentas.tsx` are deleted outright — no manual reference list, no declared balance, no screen.
- `income.accountId` (previously a nullable FK into `accounts`) becomes `income.origin`, a plain nullable text column the user types directly in the income form (e.g. "Efectivo", "TDD", "Préstamo personal", anything) — still purely descriptive, still never read by any calculation (`useDashboardSummary`, `financial-health`, `debtLimit`, `simulator` all ignore it, exactly as before).
- `expenses.accountId` and `debtPayments.accountId` columns are dropped, as already decided — nothing captures or reads them.
- `useDashboardSummary`'s `realBalanceCents`/`projectedBalanceCents` (and the account-balance projection call `projectAccountMovements`) are removed; the Inicio "SALDO" card is replaced by a single "Disponible" figure (already computed as `availableCents`) — no real/projected split, since projection was purely account-ledger-based (`src/services/recurring/projection.ts` becomes unused and is removed).
- **Alternative considered (the originally-implemented version)**: keep `accounts` as a manually-declared, editable-anytime reference list, with income tagging one of its rows. Rejected on further testing — it added a whole screen and a table for a number nobody reads and a catalog nobody needed constrained. A free-text field gets the same descriptive benefit (see specs/income) with none of the upkeep.
- This closes what was previously Open Question 4 (whether declared balances should be editable anytime) — moot, since the declared-balance concept no longer exists.

### 7. Screens keep stale data after navigating away and back — needs focus-based refetching
Found during manual testing: `src/app/(drawer)/_layout.tsx` uses `expo-router/drawer` (a React Navigation drawer navigator), which keeps every visited screen mounted indefinitely rather than unmounting it on blur. Every data hook in the app (`useBudgetRules`, `useDebts`, `useDashboardSummary`, `useDebtLimit`, `useDebtReserves`, etc.) fetches exactly once, in a plain `useEffect` on mount (confirmed: zero uses of `useFocusEffect`/`useIsFocused` anywhere in `src/`). Concretely, this surfaced as: open Deudas with no active budget rule (blocked with an alert) → navigate to Reglas Presupuestarias, create and activate a rule → navigate back to Deudas, which never remounted, so it still shows "no active rule" and keeps blocking debt creation.
- **Decision**: add `useFocusEffect` (from `expo-router`/`@react-navigation/native`) to call each affected hook's existing `refresh()` whenever its screen regains focus, starting with `useBudgetRules` (the one that broke) and auditing every other hook whose backing data can change from a different screen.
- **Alternative considered**: switch the drawer to `unmountOnBlur` per-screen, forcing a full remount (and thus a fresh fetch) every time. Rejected — it throws away in-progress form state on every navigation (e.g. a half-filled "Nueva deuda" form) for a problem that's really about stale reads, not about needing a clean screen; `useFocusEffect` fixes the actual cause without that side effect.
- This is a pre-existing gap (not introduced by this change) that this change's new hard dependency (Deudas blocking on the active rule) was the first thing to make visibly broken — worth fixing here since it directly blocks this change's own golden path, even though the root cause predates it.

### 5. Categories removal and the savings-ratio gap
`categories`, `categoriesDao`, `useCategories`, and every `categoryId` column are removed. The one real consumer of category tagging was `savingsTotalCents` in `useDashboardSummary.ts` (`expenses` where `categoryById.get(categoryId)?.budgetGroup === 'ahorro'`). With categories gone, there is no signal left to distinguish "savings" from any other expense.
- **Decision**: drop `savingsTotalCents`/`savingsRatioPct` from `financial-health` and the dashboard entirely for this change. `computeFinancialHealth` keeps only the debt-ratio-vs-limit logic (`riesgo`/`crítico` from `debtRatioPct` vs. the rule's debt-limit row; `atencion` only from being within the attention margin of that limit). This is a real behavior reduction (today "atención" can also trigger from low savings), called out below as an Open Question rather than silently designed around, since re-adding a "savings" concept later (e.g., a dedicated budget-rule type the user marks as savings, mirroring decision #1) is a reasonable follow-up but is out of scope here.

### 6. Debt "Tipo" is a label snapshot, not a live foreign key
`debts.budgetGroupLabel` (text) stores the chosen allocation label's **text** at the time the debt is created/edited — not a foreign key to `budgetRuleAllocations.id`. Per-type compliance (Inicio) groups debts by matching `budgetGroupLabel` against the active rule's current allocation labels.
- **Alternative considered**: foreign key to the specific `budgetRuleAllocations` row. Rejected — allocations belong to a rule, and rules get replaced wholesale when the user activates a different one (`reglas-presupuestarias.tsx` lets you switch active rule any time); a hard FK would orphan every debt's type the moment the user switches rules. A text snapshot degrades gracefully (a debt just shows "sin tipo en la regla activa" if the label no longer exists in whichever rule is active) instead of breaking.

### 8. Financial health becomes "worst status across all monitored groups," not "debt ratio only"
`computeFinancialHealth` no longer takes a single `debtPaymentsCents`/`debtLimitPct` pair. It now takes the list of monitored `BudgetComplianceRow`s (already computed by `computeBudgetCompliance` for Inicio's per-section card, just filtered to monitored ones) plus `availableCents`, and returns the worst individual row's status (`saludable` < `atencion` < `riesgo` < `critico`), with a negative-`availableCents` override forcing `critico` regardless. Zero monitored rows → `sin_limite`.
- **Alternative considered**: keep health status debt-specific, and let "Necesidades" have its own separate indicator with no bearing on the overall traffic light. Rejected per explicit user request — they want the overall status to reflect *any* monitored group being over/near its limit, not just debt.
- This makes `debtLimit.ts` (`computeDebtCapacity`) and `useDebtLimit.ts` fully dead code — they were already unused by any screen (the simulator was built against per-Tipo capacity via `sumActiveMonthlyCommitmentByType`, never against this module) even before this decision. Both are deleted as part of this change rather than left orphaned.

### 9. Budget rules gain edit and delete
Surfaced as a real gap once monitoring became something the user needs to adjust after the fact (e.g. realizing they forgot to mark "Deudas" as monitored): there was no way to fix a saved rule short of recreating it. `budgetRulesDao` gains `updateBudgetRule(id, name, allocations)` (replacing all allocation rows, same validation as create) and `deleteBudgetRule(id)`. Deleting the active rule is blocked with a message asking the user to activate a different rule first, rather than silently leaving the app with no active rule mid-action.
- **Alternative considered**: allow deleting the active rule, leaving no rule active. Rejected — that's exactly the "no active rule" state that blocks debt creation and clears all compliance/health display; better to make the user explicitly choose their next active rule first than have that happen as a side effect of a delete tap.

### 10. Padre/normal is a persisted column, not just a creation-time form choice
Found during manual testing: `deudas.tsx`'s "¿Padre o normal?" selector only existed in the form's local state — nothing wrote it to `debts`. Once saved, a "normal" debt and a freshly-created "padre" debt with zero children were indistinguishable in the database (both have `parentDebtId = null`), so the UI's "+ Agregar hija" button — gated only on `hasChildren` — showed up for every top-level debt, including ones the user explicitly created as "normal."
- **Decision**: add `debts.isParent` (boolean, default `false`), set directly from the form's `kind` choice at creation. `deudas.tsx` gates "+ Agregar hija" on `debt.isParent`, not on `hasChildren`.
- **Alternative considered**: infer "is this a parent" from `hasChildren` (current behavior). Rejected — that's precisely the bug; a parent with zero children so far must still offer to add its first child, and a normal debt must never offer to add any, and only a persisted flag can tell those two zero-children cases apart.

### 11. Reserve accrual seeds `reserveLastAccrualDate` to the creation date, not `null`
Found during manual testing: creating a recurring bimestral debt with a starting reserve of $750 (of $1,000) on September 30 — the last day of the month — immediately showed $1,000 in Apartados. Root cause, traced in `computeOccurrences.ts`: when `reserveLastAccrualDate` is `null` at creation, the reserve-accrual pass treats `from = anchor = debt.startDate` (today), and `computeOccurrences(SEMIMONTHLY_FIXED, anchor=today, from=today, to=today)` correctly reports today itself as a cutoff whenever today happens to be the 15th or the last day of the month — which it was. The debt's own creation-time reconciliation call (already run to materialize this month's payment if its due day already passed) then accrues one extra cutoff's worth on top of the manually-seeded starting reserve, on the very same day it was entered.
- **Decision**: when creating a debt, seed `reserveLastAccrualDate` to its `startDate` (the creation date) instead of leaving it `null`. This tells the reserve-accrual pass "the starting reserve already reflects reality as of today — only accrue for cutoffs strictly after today," which is exactly what a user-entered "Apartado inicial" is supposed to mean.
- **Alternative considered (what the user initially suggested)**: add a separate "fecha de mi último pago" input, specifically for bimestral debts, and compute elapsed cutoffs from that date instead of from creation day. Rejected as unnecessary complexity — the "Apartado inicial" amount the user already enters is itself the true current state ("as of today, I have $750"); the bug was purely that creation day got re-processed as if it were still pending, not that the app lacked a way to know history. Anchoring to creation day fixes it with no new field.
- **Confirmed with the user**: the MX quincena cutoff pattern used for reserve accrual (día 15 y último día del mes) is correct and needed no change — the app already never uses a debt's own payment day to split its reserve, exactly as the user wanted; this was purely the off-by-one seeding bug above.

### 12. A global, month-independent "Disponible" is the dashboard's primary figure
Found during manual testing: the dashboard computed everything per active month (`useDashboardSummary` filters income/expenses/confirmed-payments by `activeMonth`), so money entered in September showed as $0 once October began until the user manually scrolled the month back. This never matched the user's consistently-stated mental model of one persistent pool of money. The account-based "saldo real" that used to approximate a running total was removed earlier in this change (decision #4), leaving no month-independent figure at all.
- **Decision**: add `globalAvailableCents` = sum(all income) − sum(all expenses) − sum(all confirmed debt payments), across all dates, computed independently of `activeMonth`, and show it as the dashboard's primary figure above the month navigator. The existing per-month card stays below as a breakdown, with its net row relabeled "Balance del mes" so there aren't two differently-scoped figures both called "Disponible."
- Because recurring transactions only materialize occurrences up to today (reconciliation never generates future-dated rows), "sum of all rows" equals "sum through today" — so the all-time sum is exactly the user's true current money, with no future income leaking in.
- **Decision (confirmed with user)**: the global figure does NOT subtract reserve accruals ("Apartados"). Reserved money is physically still held; it's an earmark, not a withdrawal. The user picked "dinero que tengo" over "dinero libre." Apartados remains the place to see earmarks.
- **Alternative considered**: carry each month's leftover into the next month as an opening balance. Rejected — more moving parts (opening-balance rows, ordering) for the same result a straight all-time sum gives for free, and it muddies the per-month breakdown.

### 13. Full data reset lives in Configuración behind a destructive confirm
The user needs to wipe everything and re-enter from scratch to validate the restructured app. 
- **Decision**: a reset routine empties every user table in FK-safe order (debt payments and recurrence/reserve occurrences first, then income/expenses/recurring transactions, then debts, then budget-rule allocations and rules, then simulations, monthly summaries, and settings), returning the app to first-launch state; it also clears any in-memory store state (active month resets to current, active-rule id to null). The user chose a full wipe including budget rules ("borrar todo"), not a partial one.
- **Decision**: it is gated behind an explicit destructive confirmation dialog (not a bare button), to prevent accidental taps. No separate typed-phrase step — a single clearly-worded destructive confirm is enough for a local, single-user app the person controls.
- **Alternative considered**: delete the SQLite file and re-run migrations on next launch. Rejected — deleting all rows keeps the schema/migration journal intact and avoids a mandatory app restart; the user sees empty screens immediately as the focus-refetch (decision #7) re-reads the now-empty tables.

### 14. Recurring debts auto-deduct per quincena via auto-confirmed payment rows (supersedes the reserve/confirm model)
Found during manual testing: adding a recurring debt did nothing visible — disponible stayed flat and its budget section stayed empty — because (a) disponible only counts CONFIRMED debt payments, (b) recurring debts only generated SCHEDULED (unconfirmed) payments the user had to confirm by hand, and (c) reserves accrued separately but, by decision #4/#12, never touched disponible, and by decision #11 didn't even count the creation-period cutoff. The user confirmed (4 questions) they want the opposite: money should leave automatically as each quincena passes, no manual confirmation, with the current quincena counting at creation, and the starting reserve acting as external money that offsets the first deductions. This decision supersedes the relevant parts of decisions #2, #3, #11, and the "reserves don't reduce disponible" stance.

**Mechanism — reuse the confirmed-payment pipeline instead of a new formula.** disponible already = all income − all expenses − all *confirmed* debt payments, and per-section compliance already groups *confirmed* payments by `budgetGroupLabel`. So rather than inventing a parallel "subtract reserves" formula in two places, reconciliation generates **auto-confirmed** `debtPayments` rows (status `confirmed`) on each quincena cutoff for recurring parent/standalone debts. Then disponible and compliance both reflect the deductions with ZERO formula changes — the money and the per-section occupancy fall out of the existing pipeline. This also mirrors how recurring income already works (reconciliation generates income rows on occurrences).

**Rules:**
- `perQuincena = round(periodTotal / N)`, N = 2 (`mensual`) / 4 (`bimestral`); `periodTotal` = standalone's own amount, or the parent's live derived children sum (re-derived each run).
- Generation is driven by the **debt** (its `isRecurring`/`periodicity`/`startDate`), iterating debts directly — not by a `recurringTransactions` row. The old "create a `debt_payment` recurringTransaction" step is removed; `recurringTransactions` now only serves recurring income.
- Cutoffs are the existing `SEMIMONTHLY_FIXED` pattern (15th + last day). The **current period counts immediately**: generation starts from the most recent cutoff on or before `startDate` (so a debt created Oct 2 generates for the Sep 30 cutoff at once). This reverses decision #11's "seed to creation date so the current cutoff doesn't count" — now it must count.
- `reserveLastAccrualDate` becomes the per-debt catch-up marker (last cutoff already generated), so reopening the app applies every missed cutoff once, idempotently.
- Starting reserve (`apartado inicial`, stored in `reserveAccumulatedCents`) is a **consumable offset buffer**: each cutoff, `deducted = max(0, perQuincena − buffer)`, `buffer -= min(buffer, perQuincena)`; a confirmed-payment row is written only for `deducted > 0`. So prior savings reduce the first deduction(s) until exhausted.
- The payment day (`dueDate`) no longer drives deduction timing; it drives only the Inicio "próximos pagos" reminder (next `dueDate` occurrence, computed on the fly).
- **Confirmation is removed entirely**: no `confirmPayment`, no "Confirmar pago" button, no scheduled→confirmed flow; the Inicio card becomes an informational reminder (user's choice: keep as reminder, not remove).
- **Non-recurring debts** deduct their full total once (offset by apartado inicial) — a one-time incurred obligation.
- **Income** is unchanged and already correct for the user's "only future paydays" choice: recurring income materializes rows on each occurrence from its anchor forward, so a past payday isn't re-added (no double-count of the initial manual income).

**Deliberately deferred (flagged, not built in this pass), to keep the change reviewable:**
- Finite-debt capping: a debt with `remainingPayments` should stop deducting after its months elapse; and child MSI should expire over time now that confirm (which used to decrement them) is gone. Both are compute-from-elapsed-time refinements noted for a follow-up; the user's current test data (indefinite despensa, nómina, ongoing Luz) doesn't exercise them yet.

- **Alternative considered**: compute the deduction on read (no rows), adding a "− committed" term to the disponible formula and the compliance grouping. Rejected — it would duplicate the apartado-offset and current-period logic in two separate calculations, whereas generating auto-confirmed rows reuses the single existing confirmed-payment pipeline and stays consistent with recurring income.

## Risks / Trade-offs

- **[Risk]** No debt-limit row configured on the active rule → every debt-limit-dependent screen (Inicio health, Presupuesto capacity, Simulador) loses its reference point. → **Mitigation**: decision #1's explicit null-state UI instead of a silent wrong number; debt creation is blocked with a clear message pointing to Reglas Presupuestarias.
- **[Risk]** Dropping `savingsRatioPct` changes existing health-status behavior (fewer paths to "atención"). → **Mitigation**: flagged as Open Question; existing `health.test.ts` scenarios that rely on savings ratio need explicit review/removal in `tasks.md`, not silent deletion.
- **[Risk]** Destructive schema change — `categories` and `commitments` tables/data are dropped with no migration/export path. → **Mitigation**: acceptable for a single-user local dev app per user's explicit removal requests; called out here so it isn't a silent side effect discovered later. No production users/backups are affected.
- **[Risk]** Reserve accrual and scheduled `debtPayments` are independent mechanisms keyed off the same debt; a user could confirm a payment (resetting the reserve) for a cycle where the reserve hadn't actually finished accruing (e.g., pays early). → **Mitigation**: acceptable — the reserve is a planning aid, not a ledger; resetting early just means the next cycle starts fresh, which matches "I already paid it" reality better than blocking the reset.
- **[Risk]** A rule can be switched while debts reference the old rule's labels via `budgetGroupLabel` text snapshot (decision #6), so per-type compliance can show "sin tipo" for every debt right after switching rules. → **Mitigation**: acceptable/expected — surfaced clearly in the UI rather than mis-mapping labels across unrelated rules; the user can re-edit each debt's Tipo after switching rules.
- **[Risk]** A free-text `income.origin` (decision #4) has no validation/catalog, so the same account can end up spelled inconsistently ("Efectivo", "efectivo", "EFECTIVO") across entries. → **Mitigation**: accepted — the field is purely descriptive/historical (never grouped or aggregated by any calculation), so inconsistent spelling has no functional effect, only a cosmetic one in the income list.
- **[Risk]** Other screens may share the same stale-data-on-refocus gap as `useBudgetRules` (decision #7) but weren't caught by manual testing yet. → **Mitigation**: the fix is applied hook-by-hook as an explicit audit task in `tasks.md`, not assumed complete after fixing only the one hook that broke.
- **[Risk]** Auto-deduct (decision #14) generates a confirmed `debtPayments` row per debt per quincena forever, so rows accumulate over time. → **Mitigation**: acceptable — same growth profile as recurring income rows; a single user's local SQLite easily handles it. Catch-up is idempotent via `reserveLastAccrualDate`, so reopening never double-generates.
- **[Risk]** Removing confirmation also removes the old path that decremented child MSI `remainingPayments`, so finite debts/children won't "finish" on their own yet (deferred in decision #14). → **Mitigation**: explicitly flagged as a follow-up, not silently dropped; current test data doesn't hit it, and the fix is a contained compute-from-elapsed-time change when needed.
- **[Risk]** With multiple monitored rows now driving overall health status (decision #8), a user could monitor a group they don't actually care about and get a misleading `riesgo`/`crítico` status. → **Mitigation**: accepted — monitoring is opt-in per row, entirely the user's choice; unmonitoring a group they don't want tracked is one tap away in Reglas Presupuestarias (now that edit exists, decision #9).

## Migration Plan

Local SQLite, single device, no staged rollout — a single Drizzle migration:
1. Add new columns to `debts` (`budgetGroupLabel` nullable, `periodicity` nullable, `isRecurring` boolean default `false`, `reserveAccumulatedCents` default `0`, `reserveLastAccrualDate` nullable) and to `budgetRuleAllocations` (`isMonitored` boolean default `false`, any number can be `true` per rule). Existing debt rows keep working (no type/periodicity/reserve until the user edits them) — not retroactively blocked; new debt creation only requires an active rule to exist (for Tipo options), never a monitored row.
2. Drop `categories`, `commitments`, `accounts` tables; drop `categoryId` columns (`income`, `expenses`, `recurringTransactions`); drop `accountId` columns (`expenses`, `debtPayments`); convert `income.accountId` into a free-text `income.origin` column; drop `settings.debtLimitPct`.
3. Remove dead code in the order tasks.md lays out (DAOs/hooks/screens/services), so nothing references a dropped column before the schema migration lands.
- **Rollback**: revert the migration commit; since this is local-only, there is no external system depending on the intermediate state.

## Open Questions

1. **Recurring non-debt expenses** (e.g., a pure Netflix expense not modeled as a debt) — does Movimientos need its own "¿es recurrente?" path for expenses too, or is every periodic expense expected to be registered as a "deuda normal" going forward? Left open per the exploration conversation; `tasks.md` assumes the latter (no recurring-expense path in Movimientos, only recurring income) until confirmed otherwise.
2. **Dropping the savings ratio (decision #5)** — confirm this is acceptable, or specify what should represent "savings" now that categories are gone. Note this could now piggyback on decision #1's generalized monitoring (e.g. a monitored "Ahorro" row) rather than needing its own bespoke mechanism, if the user wants it back later.
